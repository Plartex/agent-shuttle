# Политика безопасности

[English version / Английская версия](SECURITY.md)

В этом документе описаны архитектура безопасности, границы доверия, известные эксплуатационные риски и порядок сообщения об уязвимостях в Agent Shuttle.

---

## Привязка к localhost и отсутствие сетевой аутентификации

- **Только интерфейс Loopback:** Серверы Agent Shuttle привязываются исключительно к адресу `127.0.0.1`.
- **Отсутствие сетевой аутентификации:** Эндпоинты HTTP A2A (`/`, `/bridge/*`) **не имеют встроенной аутентификации и шифрования**. Любой локальный процесс или пользователь на том же компьютере может подключиться к открытому порту Bridge, отправлять задачи агентам или просматривать текущие квоты аккаунтов.
- **Запрет публикации наружу:** Никогда не привязывайте порты Agent Shuttle к `0.0.0.0` и не публикуйте их в локальной сети или интернете без реверс-прокси (например, Nginx, Caddy), обеспечивающего терминацию TLS и строгую авторизацию.

---

## Явные риски режима `full_access`

Политика `full_access` (а также флаг `--agy-dangerously-skip-permissions` для Antigravity) полностью отключает подтверждение вызовов инструментов:

1. **Действие на весь запущенный сервер:**  
   Включение `full_access` действует на **весь запущенный процесс сервера Bridge** и на все последующие шаги выполнения. Режим не ограничен отдельным запросом или каталогом.
2. **Выполнение произвольных команд:**  
   В режиме `full_access` агент может выполнять любые команды командной строки, читать и перезаписывать файлы за пределами рабочего каталога и изменять системные настройки с правами текущего пользователя ОС.
3. **Недоверенные задачи:**  
   Никогда не передавайте непроверенный сторонний код, потенциальные промпт-инъекции или сомнительные инструкции агенту, работающему в режиме `full_access`. Для анализа недоверенного кода изолируйте Agent Shuttle внутри виртуальной машины или защищенного контейнера.

## Политики инструментов против песочниц операционной системы

- Политики инструментов Agent Shuttle (`no_tools`, `read_only`, `workspace_write`) ограничивают выбор инструментов на уровне логики харнесса.
- **Они не являются системной песочницей ОС.** Хотя `read_only` блокирует модифицирующие инструменты, внутренние процессы рантайма могут создавать временные файлы или кеши.
- **Ограничение Antigravity CLI:** CLI Antigravity в headless-режиме не предоставляет надежной песочницы только для чтения. Agent Shuttle намеренно отклоняет запросы `read_only` и `no_tools` для Antigravity до запуска модели, предотвращая ложное ощущение защищенности.
- Для гарантированной изоляции файловой системы и сетевого стека запускайте задачи внутри контейнеров ОС (Docker, Podman) или сред виртуализации.

## Управление учетными данными и секретами

- **Никаких секретов в профилях:** Не сохраняйте API-ключи, пароли и токены аутентификации в файлах `profile.json`. Используйте поле `credential_env` для указания переменной окружения.
- **Ограничение адреса Ollama:** Agent Shuttle разрешает эндпоинты Ollama исключительно на локальном адресе loopback (`127.0.0.1`, `localhost`, `::1`). Удаленные адреса без авторизации отклоняются.
- **Логи выполнения:** Проверяйте содержимое каталога `.runtime/*.log` перед отправкой логов: тексты промптов, ответы моделей и стектрейсы могут содержать фрагменты исходного кода или переменных окружения.

## Сообщение об уязвимостях

- **Канал сообщений:**  
  В настоящее время для данного репозитория **не настроен** отдельный приватный адрес электронной почты для отчетов об уязвимостях.
- Если вы обнаружили потенциальную уязвимость, воспользуйтесь приватным сообщением об уязвимости GitHub, если эта функция включена в репозитории, либо свяжитесь с владельцем репозитория напрямую.
- **Ответственное раскрытие:**  
  **Не публикуйте** описания уязвимостей, токены доступа, учетные данные API или готовые эксплойты в открытых публичных обсуждениях и issue.
