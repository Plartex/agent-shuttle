# Участие в разработке Agent Shuttle

[English version / Английская версия](CONTRIBUTING.md)

Благодарим вас за интерес к развитию проекта Agent Shuttle. Проект представляет собой модульный локальный мост взаимодействия между различными средами разработки агентных систем. Пожалуйста, следуйте данным рекомендациям при разработке, тестировании и написании документации.

---

## Настройка среды разработки

1. **Создание виртуального окружения (Windows):**
   ```powershell
   & .\Install.ps1
   ```
   Скрипт создаст окружение `.venv` и установит пакет в режиме разработки (`pip install -e .`).

2. **Чистота репозитория:**
   - Не добавляйте в Git учетные данные аккаунтов, персональные API-ключи и скомпилированные бинарные файлы.
   - Сгенерированные файлы конфигурации (`.codex/config.toml`, `.agents/mcp_config.json`) и логи выполнения (`.runtime/`) внесены в `.gitignore` и не должны попадать в коммиты.

---

## Процесс разработки через тестирование (TDD)

Мы придерживаемся строгой методологии Test-Driven Development как при исправлении ошибок, так и при реализации новой функциональности:

1. **Сначала воспроизводящий тест:**  
   Перед изменением логики бэкендов или рантаймов напишите офлайн-тест в каталоге `tests/`, воспроизводящий проблему или фиксирующий требуемое поведение протокола.
2. **Минимальная реализация:**  
   Внесите изменения в код, достаточные для прохождения регрессионного теста, сохраняя обратную совместимость.
3. **Проверка офлайн-набора:**  
   Убедитесь, что все существующие и новые модульные тесты успешно проходят.

## Запуск тестов

### 1. Основной офлайн-набор тестов

Основной набор тестов построен на имитационных (fake/mock) бэкендах. Он выполняется полностью локально без доступа к сети, учетных записей или расхода модельных квот:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Перед отправкой изменений в репозиторий обязательно проверьте, что все тесты из этого набора проходят успешно.

### 2. Выборочные тесты с реальными моделями (Opt-In Live Tests)

Тесты с обращением к реальным моделям по умолчанию пропускаются. Запускайте их осознанно при проверке локальных интеграций:

- **Интеграция с реальной Ollama (OpenCode и Claude Code):**
  Требует запущенного сервиса Ollama (`http://127.0.0.1:11434`) с установленной моделью:
  ```powershell
  $env:BRIDGE_LIVE_OLLAMA_MODEL = 'qwen3.5:9b'
  # При необходимости переопределите пути к бинарникам:
  # $env:BRIDGE_LIVE_OPENCODE_COMMAND = 'C:\tools\opencode.exe'
  # $env:BRIDGE_LIVE_CLAUDE_COMMAND = 'C:\tools\claude.exe'
  .\.venv\Scripts\python.exe -m unittest tests.test_live_ollama -v
  ```

- **Интеграция с Antigravity в режиме полного доступа:**
  Тестирует выполнение команд через реальный `agy` в изолированном временном каталоге:
  ```powershell
  $env:BRIDGE_LIVE_AGY_FULL_ACCESS = '1'
  # Опциональная проверка через временный сервер A2A:
  $env:BRIDGE_LIVE_AGY_A2A_FULL_ACCESS = '1'
  # Опциональное переопределение пути к бинарнику:
  # $env:BRIDGE_LIVE_AGY_COMMAND = 'C:\path\to\agy.exe'
  .\.venv\Scripts\python.exe -m unittest tests.test_live_antigravity_permissions -v
  ```

## Требования к документации

При изменении или добавлении документации:

1. **Двуязычный паритет:**  
   Английский язык (`README.md`, `docs/*.md`) является каноническим/основным. Русскоязычная документация (`README.ru.md`, `docs/ru/*.md`) должна быть ее полным и семантически точным эквивалентом.
2. **Взаимные ссылки между языками:**  
   Каждый документ на английском языке должен содержать ссылку на русский аналог в верхней части, и наоборот.
3. **Корректность относительных ссылок:**  
   Убедитесь, что все относительные ссылки в формате Markdown ссылаются на существующие файлы.
4. **Проверка соответствия коду:**  
   Все команды CLI, имена параметров, сигнатуры методов и схемы JSON должны в точности соответствовать текущей реализации в пакете `agent_bridge/`.
