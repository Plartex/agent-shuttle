# Архитектура и протокол Agent Shuttle

[English version / Английская версия](../architecture.md)

Agent Shuttle спроектирован как модульный слой взаимодействия для локальной разработки, соединяющий автономные агентные среды без передачи конфиденциальных учетных данных через сетевые границы. В этом документе описаны общая архитектура, протокольные решения, контроль жизненного цикла процессов и управление сессиями.

---

## Общая топология системы

```
+─────────────────────────────────────────────────────────────+
|                     Клиентское приложение                   |
|       (Python API / BridgeClient / внешний вызов)           |
+──────────────────────────────┬──────────────────────────────+
                               | A2A 1.0 JSON-RPC (HTTP)
                               v
+─────────────────────────────────────────────────────────────+
|               Сервер Agent Shuttle A2A (Starlette)           |
|  - Маршруты протокола A2A JSON-RPC (/)                      |
|  - Визитная карточка агента (/.well-known/agent-card.json)  |
|  - Read-Only эндпоинты инспекции (/bridge/*)                |
|  - SessionManager (многошаговые ходы, блокировки, очистка)  |
+──────────────┬───────────────┬───────────────┬──────────────+
               |               |               |              |
               v               v               v              v
         +-----------+   +-----------+   +-----------+  +-----------+
         |  Бэкенд   |   |  Бэкенд   |   |  Рантайм  |  |  Рантайм  |
         |   Codex   |   |Antigravity|   | OpenCode  |  |Claude Code|
         +-----+-----+   +-----+-----+   +-----+-----+  +-----+-----+
               |               |               |              |
         +-----v-----+   +-----v-----+   +-----v-----+  +-----v-----+
         |   Codex   |   |    agy    |   | opencode  |  |  claude   |
         |App Server |   |  Headless |   |   serve   |  |   print   |
         +-----------+   +-----------+   +-----------+  +-----------+
```

Для вызова инструментов между самими агентами используются мосты Model Context Protocol (MCP), работающие через stdio:

```
Codex ──── MCP ask_antigravity ─── A2A (HTTP 127.0.0.1) ─── agy CLI ─── Antigravity
Antigravity ── MCP ask_codex ──── A2A (HTTP 127.0.0.1) ─── Codex SDK ─── Codex
```

## Архитектурные принципы

1. **Только локальный интерфейс (`127.0.0.1`)**:  
   Серверы привязываются исключительно к адресу loopback. Сетевые порты не открываются наружу по умолчанию.
2. **Отсутствие передачи учетных данных**:  
   Аутентификация осуществляется локально внутри каждого харнесса (токен Codex App Server, аккаунт Google в Antigravity, локальная Ollama). Bridge никогда не передает API-ключи моделей через протокол A2A.
3. **Изоляция по умолчанию и сессии по требованию**:  
   Каждый одиночный вызов `ask()` выполняется в чистом, изолированном контексте. Многошаговые сценарии используют явный объект `BridgeSession`, который фиксирует параметры и сохраняет состояние на стороне сервера.
4. **Быстрая проверка готовности (Readiness Check)**:  
   Эндпоинт `/bridge/identity` позволяет клиентам и менеджеру процессов (`connect_harness`) за миллисекунды подтвердить тип бэкенда, рабочий каталог и режим разрешений без запуска тяжелых дочерних процессов CLI или запросов к языковым моделям.

## Описание подсистем

### 1. Бэкенд Codex (`agent_bridge.backends.CodexBackend`)
- Взаимодействует с локальным сервером Codex App Server через официальный Python SDK `openai-codex` (`AsyncCodex`).
- Создает потоки диалога, привязанные к каноническому каталогу проекта.
- Настраивает уровень рассуждений на уровне треда (`model_reasoning_effort`).
- Песочница: транслирует `tool_policy` в нативные варианты `Sandbox` (`workspace_write`, `read_only`, `full_access`). Режим `no_tools` отклоняется как неподдерживаемый.
- Квоты: считывает данные из метода `account/rateLimits/read`.

### 2. Бэкенд Antigravity CLI (`agent_bridge.backends.AntigravityCliBackend`)
- Запускает официальный исполняемый файл `agy` в headless-режиме:
  - Одиночные задачи: `agy -p <промпт> --output-format json --print-timeout <N>s`.
  - Постоянные сессии: `agy --input-format stream-json --output-format stream-json --print-timeout 30m`.
  - Повтор preflight-запроса: автоматически повторяет запуск при возникновении известных таймаутов TLS при проверке аватара профиля (до 3 попыток).
  - Выявление мягких отказов (Soft Denials): отслеживает ситуации, когда `agy` возвращает `SUCCESS` с заблокированными инструментами или пустым ответом, и выбрасывает исключение `AntigravityPermissionDenied`.
  - Сериализация чтения метаданных: блокировка предотвращает параллельный запуск нескольких экземпляров CLI при одновременных HTTP-запросах к `/bridge/info`.

### 3. Рантайм OpenCode (`agent_bridge.opencode_runtime.OpenCodeRuntime`)
- Управляемый демон HTTP: запускает процесс `opencode --pure serve --hostname 127.0.0.1 --port <порт>` на динамическом порту loopback с автоматически сгенерированным безопасным паролем из 32 байт.
- Встроенные разрешения: передает JSON-конфигурацию политик безопасности через переменную окружения `OPENCODE_CONFIG_CONTENT`.
- Очистка окружения: удаляет сторонние облачные ключи из окружения дочернего процесса, сохраняя только системные переменные ОС и явно указанный `credential_env`.
- Поддержка Ollama: использует провайдер `@ai-sdk/openai-compatible` с вариантами моделей, соответствующими уровням рассуждений.

### 4. Рантайм Claude Code (`agent_bridge.claude_runtime.ClaudeCodeRuntime`)
- Запуск в print-режиме: выполняет команду `claude -p --output-format json --bare --strict-mcp-config ...`.
- Изолированное хранилище сессий: создает временный каталог для `CLAUDE_CONFIG_DIR` на каждую сессию.
- Возобновление диалога: инициализирует сессию с `--session-id <UUID>` и продолжает последующие ходы через `--resume <UUID>`.
- Маскирование секретов: фильтрует вывод stderr, скрывая токены аутентификации перед передачей ошибок.

## Фиксированные рабочие каталоги (Workspaces)

Рабочие каталоги проходят строгую верификацию:
- Пути преобразуются в абсолютные канонические представления (`path.resolve(strict=True)`).
- На Windows пути сравниваются с нормализацией регистра символов (`os.path.normcase`).
- **Защита подключений:** Менеджер `connect_harness()` опрашивает `/bridge/identity` уже работающего сервера. Если каталог сервера отличается от запрошенного, Agent Shuttle отказывается переиспользовать процесс и генерирует исключение `ValueError`. Это исключает случайную модификацию чужого проекта.

## Постоянные сессии (`SessionManager`)

Сессионные диалоги контролируются классом `SessionManager` в `agent_bridge/a2a_server.py`:

- **Сериализация ходов:** Каждая сессия защищена отдельным `asyncio.Lock`. Параллельные запросы с одним и тем же `session_id` выстраиваются в очередь, гарантируя выполнение только одной генерации одновременно.
- **Фиксация параметров:** Кортеж `(model, reasoning_effort, read_only, tool_policy)` фиксируется на первом шаге. Любая попытка изменить настройки внутри открытой сессии блокируется.
- **Очистка неактивных сессий:** Фоновая задача запускается каждые 60 секунд. Сессии, не проявлявшие активности более 1800 секунд (30 минут), автоматически закрываются, а связанные процессы освобождаются.
- **Подсчет дельты токенов:**
  - В потоковых сессиях Antigravity счетчики токенов являются накопительными. Bridge запоминает предыдущие значения и рассчитывает дельту за текущий ход.
  - В Codex Bridge считывает поле `usage.last`, отображающее расход именно последнего шага.

## Модель угроз и локальная безопасность

- **Граница loopback:** Изоляция опирается на уровень сетевого стека ОС (`127.0.0.1`). Любой локальный процесс любого пользователя системы может подключиться к открытому порту A2A.
- **Хранение задач:** Отдельный A2A-сервер использует `InMemoryTaskStore`, если не задан `--task-db`. Управляемые MCP-серверы сохраняют задачи в SQLite в каталоге `.agent-shuttle` рабочего проекта. Промпты, история и артефакты хранятся там без шифрования; защищайте рабочий каталог. Одной базой может владеть только один сервер. После перезапуска готовые задачи остаются доступными, а прерванные переходят в failed без повторного выполнения.
- **Границы политик:** Политики инструментов (`read_only`, `workspace_write`) обеспечиваются встроенными механизмами харнессов и не являются системной песочницей уровня ядра ОС или гипервизора. Для полной изоляции от файловой системы хоста запускайте Agent Shuttle в контейнере Docker или виртуальной машине.
