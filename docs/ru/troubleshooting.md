# Диагностика и устранение неполадок

[English version / Английская версия](../troubleshooting.md)

В этом руководстве рассмотрены частые эксплуатационные проблемы, порядок диагностики, сообщения об ошибках и методы отладки для всех поддерживаемых агентных сред в Agent Shuttle.

---

## Диагностика: Antigravity CLI или Agent Shuttle

Когда задача Antigravity завершается с ошибкой или зависает, в первую очередь необходимо локализовать проблему: возникла ли она в коде моста Agent Shuttle или во внешней утилите `agy` CLI.

### 1. Проверка доступности моста (`/bridge/identity`)

Эндпоинт `/bridge/identity` отвечает **мгновенно**, без запуска дочерних процессов `agy` и без сетевых запросов к серверам Google.

```powershell
Invoke-RestMethod http://127.0.0.1:8766/bridge/identity
```

- **Если `/bridge/identity` отвечает сразу:**  
  HTTP-сервер Bridge и менеджер сессий работают штатно. Любая задержка или зависание вызова `ask()` происходят внутри самого процесса CLI `agy`, на этапе сетевого взаимодействия с серверами Google или во время выполнения инструментов.
- **Если `/bridge/identity` возвращает 404:**  
  Работает устаревшая версия Bridge. Остановите процесс и перезапустите сервер с текущей версией библиотеки.
- **Если `/bridge/identity` возвращает таймаут или ошибку соединения:**  
  Постоянный процесс Bridge может быть остановлен, заблокирован брандмауэром или завис. Проверьте терминал, где запущен `agent-shuttle serve antigravity --workspace . --port 8766`. Если используете MCP без постоянного сервера, между запросами слушателя на этом порту может не быть.

---

### Авторизация относится к процессу CLI, а не к настольному приложению

`AntigravityAuthenticationError` означает, что `agy` не смог использовать учётную запись в том окружении, из которого его запустил Bridge. Если в диагностике есть `Access is denied` для `.gemini/antigravity-cli`, вероятная причина — ограниченный или изолированный процесс запуска; это **не доказывает**, что пользователь вышел из аккаунта. Запустите `agy models` в обычном терминале под той же учётной записью Windows. Если команда работает, запустите `agent-shuttle serve antigravity --workspace . --port 8766` из этого терминала, а не из песочницы, и повторите задачу. Если команда тоже не работает, запустите `agy` интерактивно и завершите вход. Не копируйте учётные данные в проект и не отключайте песочницу глобально.

### 2. Мягкие отказы Antigravity (`AntigravityPermissionDenied`)

**Симптом:**  
Задача прерывается ошибкой `AntigravityPermissionDenied: agy denied a required tool (...); the result may be incomplete.`

**Причина:**  
В headless-режиме (`-p`) CLI Antigravity не может интерактивно запросить подтверждение действия у пользователя. Если действие подпадает под правила `ask` или `deny` в настройках, `agy` отклоняет вызов инструмента. При этом утилита часто завершается с кодом возврата `0` и возвращает `status: "SUCCESS"`, несмотря на то что результат неполный или пустой.

**Решение:**
1. Проверьте настройки в файле `~/.gemini/antigravity-cli/settings.json`.
2. Помните о приоритете правил: `deny` > `ask` > `allow`.
3. Для headless-сценариев явно разрешите необходимые инструменты в `permissions.allow` (например, `read_file`, `list_dir`).
4. Если осознанно требуется полный доступ ко всем инструментам, перезапустите сервер с флагом `--agy-dangerously-skip-permissions` или используйте `HarnessLaunch(tool_policy="full_access")`.

### 3. Зависания и таймауты Antigravity

**Симптом:**  
Задача прерывается через 300 секунд ошибкой `TimeoutError: agy did not return a result within 300s`.

**Причина:**  
По умолчанию утилита `agy` запускается с неограниченным таймаутом вывода (`0s`), что может приводить к бесконечным зависаниям при сбоях сети или зависших командах. Agent Shuttle явно задает дедлайн 300 секунд (`--print-timeout 300s`) и принудительно завершает неотвечающие дочерние процессы.

**Решение:**
- Для длительных задач увеличьте таймаут:
  - В CLI: `agent-shuttle serve antigravity --port 8766 --agy-turn-timeout-seconds 600`
  - В Python: `HarnessLaunch(name="antigravity", url="...", workspace=..., agy_turn_timeout_seconds=600)`
- Для постоянных потоковых сессий действует независимый лимит 30 минут на каждый шаг.

---

### 4. Повторные попытки при ошибках Preflight TLS

**Симптом:**  
В логах появляются предупреждения: `eligibility check failed ... tls handshake timeout`.

**Причина:**  
На этапе инициализации аутентификации `agy` иногда сталкивается с кратковременным таймаутом TLS при получении аватара профиля пользователя до начала выполнения промпта.

**Решение:**  
Agent Shuttle автоматически распознает этот тип сетевого сбоя и повторяет запуск до 3 раз с экспоненциальной задержкой. Если ошибка сохраняется, проверьте подключение к сети и при необходимости обновите авторизацию интерактивным запуском `agy`.

---

### 5. Конфликт параллельных запросов метаданных

**Симптом:**  
Параллельные вызовы `/bridge/info` или `/bridge/capabilities` зависают или завершаются с ошибкой.

**Причина:**  
Утилита `agy` использует локальные файлы блокировок сессий. Одновременный запуск нескольких команд CLI (`models`, `/model`, `/effort`, `/usage`) приводит к взаимным блокировкам.

**Решение:**  
Agent Shuttle сериализует все запросы метаданных Antigravity с помощью внутреннего `asyncio.Lock` с таймаутом 45 секунд на команду. Не запускайте параллельные экземпляры headless CLI в одном рабочем каталоге в обход Bridge.

## Диагностика OpenCode

### 1. Проблема с оберткой `.cmd` на Windows

**Симптом:**  
`RuntimeError: OpenCode .cmd launcher cannot be supervised; set runtime_command to opencode.exe`

**Причина:**  
Пакетный менеджер npm на Windows создает bat/cmd-обертки, которые некорректно обрабатывают сигналы завершения процессов и мешают отслеживанию дерева дочерних процессов.

**Решение:**  
Agent Shuttle автоматически проверяет, ссылается ли команда на `.cmd`, и пытается найти бинарный файл по пути `<npm_prefix>\node_modules\opencode-ai\bin\opencode.exe`. При необходимости укажите прямой путь к `opencode.exe` в поле `runtime_command` вашего JSON-профиля.

### 2. Таймаут запуска демона OpenCode

**Симптом:**  
`RuntimeError: OpenCode server did not become healthy within 20 seconds`

**Причина:**  
Фоновый сервер OpenCode (`--pure serve`) не смог запуститься или привязаться к выделенному порту loopback.

**Решение:**  
Изучите вывод stderr процесса OpenCode, приведенный в тексте исключения. Убедитесь в корректности пути к рабочему каталогу и доступности провайдера моделей (например, демона Ollama).

## Диагностика Claude Code

### 1. Маскирование учетных данных в stderr

**Особенность:**  
При возникновении ошибки в Claude Code Agent Shuttle проверяет поток stderr и заменяет найденные токены (`ANTHROPIC_AUTH_TOKEN`, значения из `credential_env`) на `[REDACTED]` перед тем, как выбросить `RuntimeError`.

### 2. Совместимость с Ollama

**Симптом:**  
Claude Code не может подключиться к локальной Ollama.

**Решение:**  
Убедитесь, что в JSON-профиле заданы:
- `"provider": "ollama"`
- `"endpoint": "http://127.0.0.1:11434"`
Agent Shuttle автоматически задает переменные `ANTHROPIC_BASE_URL` (адрес loopback) и `ANTHROPIC_AUTH_TOKEN="ollama"`. Удаленные адреса для Ollama отклоняются из соображений безопасности.

## Диагностика Codex

### 1. Переменная `CODEX_HOME` на Windows

**Симптом:**  
Codex не находит локальную авторизацию или конфигурацию в неинтерактивных оболочках.

**Решение:**  
Agent Shuttle автоматически проверяет наличие `CODEX_HOME` и при отсутствии задает значение по умолчанию `~/.codex`. Если настройки хранятся в нестандартном месте, укажите переменную `$env:CODEX_HOME = 'C:\path\to\.codex'`.

### 2. Ошибка политики `no_tools`

**Симптом:**  
`ValueError: Codex cannot enforce no_tools`

**Причина:**  
Codex App Server требует наличия активной песочницы (`read_only`, `workspace_write` или `full_access`). Политика полного отключения инструментов `no_tools` не поддерживается Codex. Если необходимо запретить изменения файлов, используйте `read_only`.

## Очистка зависших процессов

На платформе Windows дочерние процессы, запущенные через venv или командные оболочки, могут оставаться в памяти при аварийном завершении родителя.

- **Автоматическая очистка процессов:**  
  При выходе из контекста `connect_harness` Agent Shuttle завершает все дерево процессов с помощью `taskkill /PID <pid> /T /F`.
- **Постоянные серверы:**
  Остановите запущенный в терминале `agent-shuttle serve` сочетанием Ctrl+C. Если сервер запущен внешним менеджером процессов, остановите его через этот менеджер после проверки процесса.
